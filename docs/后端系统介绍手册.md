# Video Content Analyzer（VCA）后端系统介绍手册

> 文档版本：v2.0.0 ｜ 适用对象：产品经理、测试同学、运维同学
> 配套文档：本文档是「系统使用与运维说明」，架构设计细节见《后端架构重构方案.md》

---

## 1. 这是什么系统

**Video Content Analyzer（视频内容分析器，简称 VCA）** 是一个内部视频处理工具，核心能力是：

1. **视频上传**：接收用户上传的视频文件，安全存储到对象存储。
2. **语音转写**：用 Whisper 模型把视频中的语音转写成文字（带时间戳的分段 + 全文）。
3. **LLM 深度分析**：基于转写文本，调用大语言模型生成结构化分析报告（摘要、重点、待办等）。
4. **实时进度**：转写/分析是耗时任务，系统通过 WebSocket 实时推送进度，替代传统轮询。

定位：10–30 人内部团队使用，单机 / 双机私有化部署（Docker Compose）。

## 2. 整体架构（一句话版）

```
浏览器/前端
    │  HTTP + WebSocket
    ▼
┌─────────────────────────────────────────────┐
│  FastAPI 服务（API 网关 + 安全中间件链）        │
│   · 上传 / 转写 / 分析 / 任务管理 / 健康检查     │
│   · 限流 · CORS 白名单 · 结构化日志 · Prometheus │
└───────────────┬───────────────┬───────────────┘
                │               │
        ┌───────▼──────┐  ┌─────▼──────┐
        │  PostgreSQL  │  │   Redis    │
        │ (任务持久化)  │  │(消息总线+   │
        │             │  │ 缓存+进度)  │
        └──────────────┘  └─────┬──────┘
                │               │ pub/sub 进度
        ┌───────▼──────┐  ┌─────▼──────┐
        │  MinIO 对象   │  │ Celery Worker│
        │  存储(视频)   │  │(转写/分析/   │
        │             │  │ 清理, 重计算) │
        └──────────────┘  └─────────────┘
```

**关键变化（相比旧版）**：
- 长任务不再阻塞 Web 进程 → 交给 Celery Worker 异步跑；
- 任务状态不再存内存 → 持久化到 PostgreSQL，重启不丢、并发安全；
- 进度不再靠前端 2 秒轮询 → WebSocket 实时推送。

## 3. 组件与服务清单

系统由 6 个容器组成（通过 `docker-compose.yml` 编排）：

| 容器 | 镜像 | 作用 | 默认端口 |
|------|------|------|---------|
| `vca-api` | 本地构建（Python 3.12 + ffmpeg） | FastAPI 接口服务 | `8766` → 容器 `8000` |
| `vca-worker` | 本地构建 | Celery Worker，跑转写 / 分析 / 清理任务 | 无（内部） |
| `vca-beat` | 本地构建 | Celery Beat，定时触发清理任务 | 无（内部） |
| `vca-postgres` | `postgres:16-alpine` | 任务 / 转写 / 分析结果持久化 | `5432` |
| `vca-redis` | `redis:7-alpine` | 消息队列 + 缓存 + 进度 pub/sub | `6379` |
| `vca-minio` | `minio/minio:latest` | 视频对象存储 | `9000`（API）/ `9001`（控制台） |

## 4. 部署与启动

### 4.1 前置要求
- 已安装 Docker 与 Docker Compose（v2）
- 网络可访问 LLM 服务商（默认 SiliconFlow：`https://api.siliconflow.cn/v1`）

### 4.2 启动步骤

```bash
cd video-analyzer

# 1. 准备环境变量
cp .env.example .env
#   编辑 .env，至少修改：POSTGRES_PASSWORD、MINIO_SECRET_KEY、LLM_API_KEY

# 2. 生成加密密钥（用于服务端加密管理 LLM API Key，必做）
python scripts/generate_key.py
#   将输出的 ENCRYPTION_KEY 填入 .env

# 3. 一键启动全部服务
docker compose up -d

# 4. 初始化数据库（首次启动；生产环境建议用 alembic upgrade head）
docker compose exec api python scripts/init_db.py
```

### 4.3 验证启动成功

```bash
# 存活探针（进程在不在）
curl http://localhost:8766/health
# 返回 {"status":"ok","service":"Video Content Analyzer","version":"2.0.0"}

# 就绪探针（依赖都正常吗）
curl http://localhost:8766/ready
# 返回各依赖检查结果：postgres / redis / minio / whisper_model

# 接口文档（Swagger UI）
# 浏览器打开 http://localhost:8766/docs
```

### 4.4 访问地址汇总

| 用途 | 地址 |
|------|------|
| API 根信息 | `http://<host>:8766/` |
| Swagger 文档 | `http://<host>:8766/docs` |
| ReDoc 文档 | `http://<host>:8766/redoc` |
| 存活探针 | `http://<host>:8766/health` |
| 就绪探针 | `http://<host>:8766/ready` |
| Prometheus 指标 | `http://<host>:8766/metrics` |
| MinIO 控制台 | `http://<host>:9001`（账号见 `.env`） |

## 5. 接口一览（API 速查表）

所有业务接口前缀为 `/api/v1`。接口均带**速率限制**（按客户端 IP 计），超出返回 `429`。

| 方法 | 路径 | 说明 | 限流 |
|------|------|------|------|
| POST | `/api/v1/upload` | 上传视频，返回 `job_id` | 5/分钟 |
| POST | `/api/v1/transcribe` | 启动异步转写任务 | 5/分钟 |
| GET | `/api/v1/transcribe/{job_id}` | 获取转写结果 | 60/分钟 |
| POST | `/api/v1/analyze` | 启动 LLM 分析任务 | 10/分钟 |
| GET | `/api/v1/analyze/{job_id}` | 获取分析结果 | 60/分钟 |
| POST | `/api/v1/test-api-key` | 校验 LLM API Key 是否有效 | 10/分钟 |
| GET | `/api/v1/jobs` | 任务列表（支持状态/类型/创建人过滤 + 分页） | 30/分钟 |
| GET | `/api/v1/jobs/{job_id}` | 单个任务详情 | 60/分钟 |
| POST | `/api/v1/jobs/{job_id}/cancel` | 取消进行中/排队中的任务 | 10/分钟 |
| DELETE | `/api/v1/jobs/{job_id}` | 删除任务及关联文件（级联删 MinIO） | 5/分钟 |
| WS | `/api/v1/ws/jobs/{job_id}` | 实时进度推送（WebSocket） | — |

> 认证说明：当前内部部署版本通过 `X-User-ID` 请求头标识操作人（用于任务归属与审计），`X-Request-ID` 用于链路追踪。对外暴露前需补充正式鉴权（见第 8 节）。

## 6. 典型使用流程

```
① 上传视频
   POST /api/v1/upload  (multipart 文件)
   → 返回 { job_id, storage_key, filename, file_size, video_duration }

② 启动转写
   POST /api/v1/transcribe  body: { "job_id": "...", "model": "tiny", "language": "zh" }
   → 返回 { job_id, status: "processing", websocket_url }

③ 订阅进度（前端）
   WS 连接 websocket_url（ws://host:8766/api/v1/ws/jobs/{job_id}）
   → 收到 { progress, message, status } 实时消息，直到 status=completed/failed

④ 获取转写结果
   GET /api/v1/transcribe/{job_id}
   → { language, duration, full_text, segments[], keywords{} }

⑤ 启动 LLM 分析
   POST /api/v1/analyze  body: { "job_id": "...", "transcription": {...}, "analysis": {...} }
   → 返回新的 analysis_job_id + websocket_url

⑥ 获取分析结果
   GET /api/v1/analyze/{analysis_job_id}
   → { report, model_used, tokens_used }
```

**进度消息格式（WebSocket）示例**：
```json
{ "type": "progress", "job_id": "abc", "progress": 42.0, "message": "转写中 42%", "status": "processing" }
```

## 7. 配置项说明（.env）

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `POSTGRES_USER/PASSWORD/DB` | `vca` / `vca_secret` / `video_analyzer` | 数据库账号，**生产必须改密码** |
| `MINIO_ACCESS_KEY/SECRET_KEY` | `minioadmin` / `minioadmin` | MinIO 账号，**生产必须改** |
| `LLM_API_KEY` | 空 | LLM 服务商密钥（服务端保管，不落前端） |
| `LLM_PROVIDER` | `siliconflow` | 可选 `siliconflow` / `ollama` / `zhipu` |
| `LLM_BASE_URL` | `https://api.siliconflow.cn/v1` | LLM 接口地址 |
| `ENCRYPTION_KEY` | 空 | 由 `generate_key.py` 生成，**必填** |
| `ALLOWED_ORIGINS` | `http://127.0.0.1:8765,...` | CORS 白名单（逗号分隔，不支持 `*`） |
| `WHISPER_MODEL` | `tiny` | 转写模型，可选 `tiny/base/small/...` |
| `WHISPER_DEVICE` | `cpu` | `cpu` 或 `cuda`（有 GPU 的机器设为 `cuda` 提速） |
| `MAX_VIDEO_SIZE_MB` | `600` | 单次上传大小上限 |
| `API_PORT` | `8766` | 对外 API 端口 |
| `PG_PORT / REDIS_PORT / MINIO_PORT / MINIO_CONSOLE_PORT` | `5432 / 6379 / 9000 / 9001` | 各服务端口 |
| `cleanup_interval_hours` | `1` | 清理任务执行周期 |
| `cleanup_max_age_hours` | `1` | 超过该时长的任务关联文件被清理 |

> ⚠️ 默认 `cleanup_max_age_hours=1` 表示 1 小时前的任务文件会被清理，内部短时使用可以；若需长期保留视频，请调大该值或关闭清理 Beat。

## 8. 安全设计要点

| 项 | 做法 |
|----|------|
| **CORS** | 白名单机制（`ALLOWED_ORIGINS`），不再允许任意来源 |
| **LLM Key 管理** | 服务端用 AES-256-GCM 加密保管，前端只传 Key 做「连通性测试」，不持久化到前端 |
| **速率限制** | 所有写接口按 IP 限流，防刷爆 |
| **文件校验** | 上传校验 MIME 类型与大小，拒绝非法文件 |
| **命令执行** | 音频提取用参数列表方式调用 ffmpeg，杜绝 shell 注入 |
| **结构化日志** | 全程 JSON 日志 + `request_id`，便于审计与排障 |
| **临时文件** | 上传时本地临时文件用完即删；历史文件由 Beat 定时清理 |

> 🔔 提醒：当前为内部部署版本，未接入统一登录鉴权。若对外或对跨部门开放，需补充正式认证（如 API Key / OAuth），请与技术负责人确认。

## 9. 运维与监控

### 9.1 健康检查（接入监控 / 负载均衡）
- `/health`：存活探针，进程在即可返回 200，不查依赖。
- `/ready`：就绪探针，检查 PostgreSQL / Redis / MinIO / Whisper 是否可用，异常返回 503。

### 9.2 指标（Prometheus）
- `/metrics`：暴露请求量、延迟、错误率等指标（已排除 `/health`、`/ready`、`/metrics` 自身）。

### 9.3 日志
- 全量 JSON 结构化日志，关键事件带 `request_id`，可用 ELK / Loki 等收集。
- 常用排查链路：用 `request_id` 串联一次请求在 API / Worker / Redis 的日志。

### 9.4 资源与数据
- 数据库数据：PostgreSQL 卷 `pgdata`
- 视频文件：MinIO 卷 `miniodata`（桶名 `video-analyzer`）
- Whisper 模型缓存：卷 `whisper-models`
- Redis 数据：卷 `redisdata`（含任务队列与进度消息，重启后队列可能丢失，属正常）

## 10. 常见问题排查

| 现象 | 可能原因 | 处理 |
|------|---------|------|
| `docker compose up` 后 API 一直 unhealthy | 依赖未就绪 / `.env` 配置错 | `docker compose logs api` 看报错；确认 PG/Redis/MinIO 已 healthy |
| 上传报 `UnsupportedMediaType` | 文件 MIME 不在白名单 | 确认上传的是 `video/*` 类型文件 |
| 上传报 `413 / FileTooLarge` | 超过 `MAX_VIDEO_SIZE_MB` | 调大 `.env` 中上限或压缩视频 |
| `/ready` 显示 `minio: bucket_not_found` | 桶未创建 | 重启 API 自动建桶，或手动建桶 `video-analyzer` |
| 转写任务一直 `processing` 不结束 | Worker 没起来 / 队列堆积 | `docker compose ps` 看 `vca-worker` 状态；`docker compose logs worker` |
| WebSocket 收不到进度 | 客户端连错 host/port；或 Redis 不通 | 确认 `ws://<api_host>:8766/api/v1/ws/jobs/{job_id}`；检查 Redis |
| LLM 分析报密钥错误 | `LLM_API_KEY` 失效 / 余额不足 | 用 `POST /api/v1/test-api-key` 验证；更新 `.env` 后重启 api/worker |
| 限流报 `429` | 触发速率限制 | 降低调用频率，或调整 `rate_limit_*` 配置 |
| GPU 机器转写仍很慢 | `WHISPER_DEVICE` 仍是 `cpu` | 设为 `cuda` 并确认驱动可用，重启 worker |

## 11. 与旧版对比（13 个历史问题修复一览）

| 历史问题 | 新版做法 |
|---------|---------|
| 服务无法启动（重复 parse_args） | pydantic-settings 统一配置，启动即校验 |
| 任务存内存 dict，并发不安全、重启丢失 | PostgreSQL 持久化，事务安全 |
| 开放 CORS + shell 注入风险 | CORS 白名单 + 参数列表调用 ffmpeg |
| API Key 明文在前端 | 服务端 AES-256-GCM 加密管理 |
| 无限流 / 无健康检查 | slowapi 限流 + `/health` + `/ready` |
| 临时文件不清理 | 用完即删 + Beat 定时清理 |
| 硬编码路径 | MinIO 对象存储，路径可配 |
| 同步阻塞、无超时重试 | Celery 异步 + 超时 + 重试 |
| 仅 CPU 转写 | `WHISPER_DEVICE` 可切 GPU |

## 12. 给各角色的同步提醒

- **产品**：功能范围与旧版一致（上传 / 转写 / 分析），交互上进度从「轮询」变为「实时推送」，需前端配合改造。
- **前端**：进度推送请改用 WebSocket（`ws://host:8766/api/v1/ws/jobs/{job_id}`），不再 2 秒轮询；上传需带正确 `Content-Type`。
- **测试**：接口变更清单见《后端架构重构方案.md》第 9 章；联调请用 `/docs` 自测；重点回归转写 / 分析异步流程与取消 / 删除。
- **运维**：生产部署前务必修改所有默认密码；接入 `/health`、`/ready`、`/metrics` 到监控；数据库与 MinIO 数据卷定期备份。
