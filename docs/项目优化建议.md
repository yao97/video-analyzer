### <a id="bug-n1"></a>Bug #N1 · 🔴 P1 — `duration` 非法值导致 500 ~~✅ 已修复~~

**文件**：`backend/transcribe_server.py` `api_transcribe()`

**原因**：`duration = float(request.form.get("duration", 60))` 直接转换，前端传 `duration=abc` 或 `-5` 时抛 `ValueError` → 500。

**修复**：try/except 包裹 + NaN/≤0/超 10 小时回退 60 秒。

### <a id="bug-n2"></a>Bug #N2 · 🔴 P1 — 转写多任务并发丢分片 ~~✅ 已修复**

**文件**：`backend/transcribe_server.py` 全局信号量 + `run_transcription()`

**原因**：多个转写任务同时运行，每个任务又开多线程 → 多个 Whisper 实例并发推理 → torch 底层线程竞争，部分分片解码失败（`KeyError: Linear(...)` / `cannot reshape tensor of 0 elements`）。实测 2 任务并发时**每个任务各丢一半分片**（8 段/4 段 vs 正常 22 段）。

**修复**：`MAX_CONCURRENT_TRANSCRIBE = 1`（强制串行），任务排队获取信号量；任务内多线程分片并行保持（已验证安全）。

> ⚠️ **运维红线：转写一次只能跑一个任务**。并发转写是 Whisper 的线程安全隐患，已在代码层强制。

### <a id="bug-n3"></a>Bug #N3 · 🟡 P2 — 模型池 `get()` 无超时 ~~✅ 已修复~~

**文件**：`backend/transcribe_server.py` `_transcribe_one()`

**原因**：`model_pool.get()` 阻塞无超时，模型实例加载失败导致池空时线程无限等待。

**修复**：`get(timeout=120)` + `queue.Empty` 兜底返回空分片。

### <a id="bug-n4"></a>Bug #N4 · 🟡 P2 — 转写后视频临时文件不清理 ~~✅ 已修复~~

**文件**：`backend/transcribe_server.py` `run_transcription()`

**原因**：转写完成后只删 WAV，视频原文件保留在 temp 目录，长期运行磁盘膨胀。

**修复**：完成后同时删除视频文件。

### <a id="bug-n5"></a>Bug #N5 · 🟢 P3 — 排队任务无状态提示 ~~✅ 已修复~~

**文件**：`backend/transcribe_server.py` + `frontend/web_player.html`

**原因**：任务排队等待转写槽位时状态仍为 `starting`，用户误以为卡住。

**修复**：新增 `waiting` 状态（progress=2，"前面有转写任务进行中，正在排队等待..."），前端 `pollTranscribeResult` 加 waiting 分支显示排队提示。

### <a id="bug-2"></a>Bug #2 · 🔴 P1 — `jobs` 字典并发不安全 ~~✅ 已修复~~

> **状态：✅ 已修复**。新增 `jobs_lock = threading.Lock()`（L115），6 处读写均已用 `with jobs_lock:` 保护。

**文件**：`transcribe_server.py`  
**位置**：第 99 行 `jobs = {}` + 第 565 行 `run_transcription` + 第 715/799/829 行 API handler

**现状**：
```python
jobs = {}  # 全局字典，无任何锁保护

# 线程 A（转写线程）：写入 jobs[job_id]
jobs[job_id] = {"status": "transcribing", ...}

# 线程 B（HTTP 请求）：读取 jobs[job_id]
return jsonify(jobs.get(job_id, {}))
```

**风险**：
- 字典在迭代中被修改 → `RuntimeError: dictionary changed size during iteration`
- 写覆盖未完成的读 → 返回状态不准确
- 两个 job 的 uuid 碰撞（极端但理论上可能）

**修复**：
```python
import threading

jobs = {}
jobs_lock = threading.Lock()

# 所有 jobs 读写统一用：
with jobs_lock:
    jobs[job_id] = {...}
```

> **状态：✅ 已修复**。旧版仅做 `mask_key()` 日志脱敏。重构后**服务端用 AES-256-GCM 加密管理 LLM API Key**（`ENCRYPTION_KEY` 环境变量 + `generate_key.py` 生成密钥）。前端只传 Key 做连通性测试，不持久化；后端不落明文字段。

### <a id="bug-6"></a>Bug #6 · 🟡 P2 — 无限流 + 无健康检查 ~~✅ 已由后端重构修复~~

> **状态：✅ 已修复**。重构后：(1) 所有写接口用 slowapi 按 IP 限流（超出返回 429）；(2) `/health` 存活探针 + `/ready` 就绪探针（查 PostgreSQL/Redis/MinIO/Whisper）；(3) `/metrics` Prometheus 指标暴露。

## 二点五、功能精简建议（产品方向）

> **2026-07-28 评估结论**：以下 4 个功能模��属于「数据驱动的自我感动」——有工程价值，无用户价值。

### <a id="design-1"></a>设计问题 #D1 · 🔴 P1 — 内容类型识别：用户不需要，准确率也堪忧

**当前行为**：9 种类型 × 5-7 条 CV 特征信号 × 权重矩阵，自动判定视频属于「电商/Vlog/医美/教育…」

**为什么没用**：

1. **用户比机器清楚**：编导上传的就是他要拆的竞品，自己知道是什么类型。判定结果不产生新信息。
2. **判定逻辑不可靠**：白底比例 > 0.28 = 电商？教育视频也用白板——判错。带货视频深色背景——漏判。纯 CV 特征无语义理解 = 随机分类器。
3. **判定结果没被下游使用**：深度拆解报告的 prompt 里根本不依赖这个类型标签，LLM 自己会重新判断。

**建议**：**砍掉**。改成让用户自己在下拉菜单选内容类型，或者直接交给 LLM 在深度分析时自动识别——LLM 做这个比 CV 矩阵准 100 倍。

---

### <a id="design-2"></a>设计问题 #D2 · 🔴 P1 — 多维分析图表：编导看不懂也不需要

**当前行为**：4 张 Chart.js 图表——RGB 趋势折线图、亮度+运动双轴图、文字密度柱状图、色调环形图。

**为什么没用**：

1. **受众错位**：这些图表是一个「视频数据科学」项目的答辩材料，不是短视频创作者的决策工具。
2. **信息冗余**：一个编导需要的结论是「整体偏暖色调，节奏中等偏快」——一句话，不用 4 张图。
3. **CPU 浪费**：在浏览器里渲染 4 个 Canvas 图表，用户不会看第二眼。

**建议**：**砍掉全部图表**。把画面分析数据直接喂给 LLM 作为上下文（已有 2.10 的 `/api/analyze-copy` 传入了帧数据），让 LLM 输出一句人类可读的风格总结，放在深度报告开头。

---

### <a id="design-3"></a>设计问题 #D3 · 🟡 P2 — 场景分段（文案结构拆解）：方向对，输出错

**当前行为**：按皮肤比例/蓝色比例/文字密度等 CV 特征自动分段，输出一列技术标签。

**为什么需要改**：

当前输出：
```
设备界面 @12s-18s | 皮肤:12% | 蓝:5% | 文字:3.5%
```

用户能懂的表达：
```
产品特写 @12s-18s | 暖光，稳定镜头，人物手持产品，背景虚化
```

**问题根源**：CV 中间变量（皮肤%、蓝色%）暴露给了用户，这不是用户语言。

**建议**：**保留框架，改输出**。Segment 信息直接传 LLM 做语义化描述，用户侧只展示人类可读的标签文本。或者直接用 Whsiper 语音分段时间戳 + 帧截图为基准分段，跳过 CV 特征判定。

---

### <a id="design-4"></a>设计问题 #D4 · 🟡 P2 — 页面 Tab 过多：用户认知负荷高

**当前行为**：7 个 Tab（总览/语音转写/视频分帧/内容图表/文案结构/完整报告/深度拆解）

**为什么需要精简**：

1. 其中 3 个 Tab 的内容是建议砍掉的（内容图表 = D2、文案结构 = D3 含无意义标签、总览 = 混合了 D1+D2 内容）
2. Tab 越多，用户第一次上手越困惑
3. 有些 Tab 的数据依赖其他 Tab，但用户不知道顺序

**建议**：精简为 4 个 Tab：

| Tab | 内容 |
|-----|------|
| **语音转写** | 转写进度 + 分段时间线 + 关键词（保留 2.4、2.5） |
| **帧预览** | 关键帧截图 + 简单标签（人物/字幕/白底/暗光），可滚动画廊 |
| **深度拆解报告** | LLM 生成的九节结构化报告，包含分镜头表、文案拆解、爆款文案库 |
| **完整报告** | Markdown 导出 + 下载按钮 |

核心指标（时长/分辨率/帧率/大小）放到左侧视频预览面板下方就行，不占 Tab。
